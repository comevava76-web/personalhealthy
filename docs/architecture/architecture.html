Functional overview

What the app does, who does what and in which order. A blood-pressure diary for Android, with a web dashboard and reports for the doctor.

The flow from the phone to the doctor

The user's path

  1. Installs the app from the public link /download (later from Google Play).
  2. Signs in with Google once, through OAuth 2.0 / OpenID Connect (a signed ID token, never the password), and gives privacy consent.
  3. Accepts the terms of use, binding, at the first installation and after every update: without acceptance the app does not open. Every acceptance is recorded (anonymous code, phone, versions, text fingerprint, date).
  4. Every day unlocks with the phone's fingerprint or PIN, and stays signed in until “Sign out”.
  5. Records a reading: by voice (SYS, DIA, PUL, checked and confirmed on screen) or by photographing the display (AI features).
  6. Looks back: last reading, the week, the Report with charts and tiles.
  7. Shares: PDF or Excel from the phone, or Web Dashboard → “Send to the doctor”.
  8. Changes phone: signs in with Google and finds everything. Signs out or deletes the account at any time.

Fixed rules

  • No diagnosis, no advice, no judgement of the values: no coloured zones, no “normal”.
  • Labels always SYS, DIA, PUL. Pressure and pulse never in the same chart.
  • Charts: 7 days, one dot per day = the mean of that day's readings (explained before the charts), value next to it, axis with day numbers only.
  • The same A4 PDF from the app and from the web; the web downloads it at once as a file.
  • No red anywhere: SYS violet, DIA teal, PUL amber. No colour means “good” or “bad”.
  • Scan is on only when Anthropic has just said yes (valid key, credit): a minimal request on opening if the last check is over an hour old, after every error and when the screen is pulled down.
  • Readings kept at most 365 days, deleted nightly; only the acceptances of the terms remain, as proof.
  • The app stays simple: the owner's controls are only in the web Admin area.

Extending

Modular: lab reports will be a new module in web.ts and app.js.

Security and data

  • Phone: a private key that never leaves the phone signs every request; the server refuses bad signatures or clocks off by more than 5 minutes.
  • Web: a 60 s one-time code in the # part of the address becomes the only cookie, hint_s (technical, 7 days, HttpOnly, Secure, SameSite=Strict), set only after the cookie notice is accepted; the choice stays in local storage. The app uses no cookies.
  • Doctor links: read-only, fixed period, expire after 7 days, withdrawable; no email, no account, no cookie.
  • Remote switch-off: the app version travels with every request; settings holds app_min_version, app_blocked, app_off. Owner only, from the web Admin area.
  • Owner's area (web, owner only): usage numbers per anonymous code (joined, last opened, readings, AI on), D1 size against the 500 MB free limit. Never readings, reports or names.
  • Subscription (ready, off until Google Play): Play Billing, checked with the Play Developer API.
  • Database: only SHA-256 fingerprints of codes, cookies and links; Anthropic keys encrypted with AES-GCM.
  • Retention: readings older than 365 days deleted every night; acceptances in an append-only register.
  • Personal data: no name, no email (of the Google account only an HMAC-SHA256 fingerprint; the email stays on the phone); photos and files processed and discarded; data in the EU.

Releasing a version

  1. Change on a branch → pull request → merge into main.
  2. GitHub Actions updates D1, deploys the Worker, builds the APK and the AAB, creates release v0.1.N and puts the APK at /download.
  3. The site changes at once; the app updates by installing the new APK.

Error log continuous testing and improvement

  • Server: every failed call to /v1 or /my/api (status 400–599, except 402, 404, 426 and a browser without a session) and every exception.
  • App: crashes (sent when the app opens again) and failures of local work such as building the PDF or the Excel file. At most 20 a session.
  • Web: script errors of the Web Dashboard, at most 5 a page; never on a doctor's link.
  • Short by design: one row per day, source, code, place and app version, with a counter. Digits are removed from messages, so no reading value is stored; only the anonymous account code. Kept 90 days.

Who uses it

  • Owner: Admin tab → “Errors of the last 30 days” and the 7-day count.
  • Developer: every morning a scheduled routine reads the report of the log and fixes (page 4); in working sessions it is also read after every release.
  • Table: error_log in D1, written by worker/src/errors.ts; app side ErrorReport in Core.kt; web side in app.js.
  • Also on every account: the app version it last opened with and whether the AI features are on, for the owner's Admin tab.

Delivery, from the chat to the phone

  1. Decide — Human describes the change in the chat; unclear points are asked, not guessed.
  2. Build and test — Claude on branch claude/…: code and documents in one commit; Worker bundle, pages in Chromium, documents rendered.
  3. Merge — pull request, Docs check green, squash merge into main.
  4. Release — GitHub Actions: D1 tables, Worker, APK/AAB v0.1.N, /download; Claude checks it and sends the APK.
  5. Try — Human tries the APK; feedback starts the next round. Rollback: revert the pull request.

Continuous improvement loop proactive: every day, without being asked

Small fixes are merged by the routine; larger ones, or the terms, wait for the human. Not automated yet: unit tests, real-phone tests.
