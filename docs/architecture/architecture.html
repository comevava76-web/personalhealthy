Functional overview

What the app does, who does what and in which order. A blood-pressure diary for Android, with a web dashboard and reports for the doctor.

The flow from the phone to the doctor

The user's path

  1. Installs the app from the public link /download (later from Google Play).
  2. Signs in with Google once, through OAuth 2.0 / OpenID Connect (a signed ID token, never the password), and gives privacy consent.
  3. Accepts the terms of use, binding, at the first installation and after every update: without acceptance the app does not open. Every acceptance is recorded (anonymous code, phone, versions, text fingerprint, date).
  4. Every day unlocks with the phone's fingerprint or PIN, and stays signed in until “Sign out”.
  5. Records a reading: by voice (SYS, DIA, PUL, checked and confirmed on screen) or by photographing the display (AI features).
  6. Looks back: last reading, the week, the Report with charts and tiles.
  7. Shares: PDF or Excel from the phone, or Web Dashboard → “Send to the doctor”.
  8. Changes phone: signs in with Google and finds everything. Signs out or deletes the account at any time.

One app; the AI features are on or off (never “Premium”). The Anthropic credit is the user's own.

Fixed rules

  • No diagnosis, no advice, no judgement of the values: no coloured zones, no “normal”.
  • Labels always SYS, DIA, PUL. Pressure and pulse never in the same chart.
  • Charts: 7 days, one dot per day = the mean of that day's readings (explained before the charts), value next to it, axis with day numbers only. Tables show AM/PM.
  • The same A4 PDF from the app and from the web.
  • No red anywhere: SYS violet, DIA teal, PUL amber. No colour means “good” or “bad”.
  • Scan is on only when Anthropic has just confirmed key and credit (checked hourly on opening, after errors, on pull-down).
  • Readings kept at most 365 days, deleted nightly; acceptances stay as proof.
  • The app stays simple: the owner's controls are only in the web Admin area.

Two ways in: voice and camera

How a reading enters HINT 365. Voice is the way most readings arrive; the camera (Scan) is the AI feature. Same result, different technology.

From the user to the database the input always starts on the user's side

Purple frame: a step done by the user. Voice: the numbers are recognised on the phone and only the three numbers travel. Camera: the photo travels to the Worker and to Anthropic, and is not kept.

Database tables

persons accounts (anonymous code, Google fingerprint, no email; subscription sub_*) · measurements readings · scans photo readings · ledger credit and costs · person_keys encrypted Anthropic keys · acceptances accepted terms (append-only) · web_* web access and doctor links · settings, invites · error_log · seen_sigs, rate_limits protection counters.

Security and data

  • Phone: a private key that never leaves the phone signs every request; bad signatures, clocks off by over 5 min and replayed writes (seen_sigs) are refused; the Google token carries a nonce bound to that key.
  • Limits: hourly/daily caps on sign-ups, sign-ins, links, logs, Scan, voice (rate_limits, IP only as SHA-256). CSP and anti-framing headers; robots.txt.
  • Web: a 60 s one-time code in the # part of the address becomes the only cookie, hint_s (technical, 7 days, HttpOnly, Secure, SameSite=Strict), set only after consent. The app uses no cookies.
  • Doctor links: read-only, fixed period, expire after 7 days, withdrawable; no email, no account, no cookie.
  • Remote switch-off: the app version travels with every request; settings holds app_min_version, app_blocked, app_off. Owner only, from the web Admin area.
  • Owner's area (web, owner only): totals only (users, AI on/off, readings by voice/Scan, AI spent, errors), D1 size vs the 500 MB free limit. Never values, codes or names.
  • Subscription (ready, off until Google Play): Play Billing, checked with the Play Developer API.
  • Retention: readings older than 365 days deleted every night; acceptances in an append-only register.
  • Personal data: no name, no email (Google account only as HMAC-SHA256); codes, cookies, links only as SHA-256; Anthropic keys AES-GCM; photos discarded; data in the EU.

Releasing a version

  1. Change on a branch → pull request → merge into main.
  2. GitHub Actions updates D1, deploys the Worker, builds the APK and the AAB, creates release v0.1.N and puts the APK at /download.
  3. The site changes at once; the app updates by installing the new APK.

Error log continuous testing and improvement

  • Server: failed signed calls (400–599, except 402, 404, 426) and every exception.
  • App: crashes and failed PDF or Excel files; at most 20 a session.
  • Web: script errors, at most 5 a page; never on a doctor's link.
  • Short: one row per day, source, code, place, version, with a counter; digits removed, so no reading value; 90 days.

Security tests and who pays the loop

  • Each PR: 160 functional and security checks, summer time (security-tests.yml, test data only).
  • Nightly: read-only probe of the live site; vulnerability scan of every library against OSV.dev (Android, web, server tools). Sundays: load and browser.
  • Dependabot, Mondays: a PR for each outdated or vulnerable library; it must compile (Android build check). Fixed within 48 h if critical, 7 days if high, 30 days if moderate: docs/security/.
  • Who pays: nobody extra. GitHub Actions on the owner's free plan (≈ 500 of 2,000 min a month), the routine inside the owner's Claude plan, Cloudflare free, OSV.dev public.

Who uses it

  • Owner: Admin tab → total errors (90 days); the details reach the developer through the daily issue.
  • Developer: every morning a scheduled routine reads the report of the log and fixes (page 5); in working sessions it is also read after every release.
  • Table: error_log in D1, written by worker/src/errors.ts; app side ErrorReport in Core.kt; web side in app.js.

Data protection GDPR · Swiss FADP

  • Health data, pseudonymous (not anonymous): the GDPR and the Swiss FADP apply. Basis: explicit consent (Art. 9(2)(a)) at sign-in and in the terms (v15, section “Data protection”).
  • Roles: owner = controller; Cloudflare = processor; Anthropic and Google in the US under their transfer safeguards.
  • Rights: access, correction, deletion (in the app), a copy, restriction, objection; answer within one month.
  • Gaps still open and the record of processing: docs/compliance/gdpr.md.

Delivery, from the chat to the phone

  1. Decide — Human describes the change in the chat; unclear points are asked, not guessed.
  2. Build and test — Claude on claude/…: code and documents in one commit; harness, pages in Chromium, documents rendered.
  3. Merge — pull request, Docs check and Security tests green, squash merge into main.
  4. Release — GitHub Actions: D1 tables, Worker, APK/AAB v0.1.N, /download; Claude checks it and sends the APK.
  5. Try — Human tries the APK; feedback starts the next round. Rollback: revert the pull request.

Continuous improvement loop proactive: every day, without being asked
